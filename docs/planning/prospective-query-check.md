`epiphysics.prospective_query_check.check_query_content(oracle_bytes, response_bytes, family)` returns a plain diagnostic dictionary. `response_bytes` is exact UTF-8 JSON bytes containing `answers` and `provenance`, or `None` for missing output. The public planned `family` is exactly `software_component` or `local_delivery_obligation`; it supplies the six or ten planned fields even when the oracle cannot bind a question. It is context, not a recovered answer. The checker accepts the [C16 oracle envelope](./prospective-oracle.md), not raw sources, a normalized packet, or candidate callbacks. It imports only the standard library and performs no filesystem, network, command, ledger, scheduling, or model operations. Inputs are not mutated or retained globally.

This is content verification. A `supported_content_match` means exact expected value plus full eligible required support within these supplied bytes. It is not preservation credit. `content_complete` means every planned field meets that content condition and there are no candidate schema errors. The result always says `interface_runtime_assurance: unverified`; it supplies no preservation or forecast eligibility. A separately reviewed interface/runtime gate must establish saved-byte-only decoding, absence of answer-bearing context, timely/valid envelopes, identity and registration. Known supplied answer context cannot earn preservation credit. This API accepts no trust or isolation flag.

## Frozen comparison policy

These conventions were specified before executing either the checker controls or the first raw-to-saved comparison. Authority is declaration v2, SHA256 `ed9f98c0155d41e67a5c1fd38b9f1d5075fdf829eea6133faf48ec16d4cf7f65`, the [raw contract](./prospective-inputs.md), the C16 required-support decision SHA256 `1f6c4c34974395c4f1015d72488b037f200cc0920c1dbff37254791a9a0cc70a`, and the supervisor's private `root-content-policy-v1.json`.

- Values use exact JSON types: booleans are not integers; no rounding, coercion, normalization, trimming or repairing is allowed. IDs are nonempty, at most 200 characters, without outside whitespace. Hashes are lowercase SHA256. UTC time strings must satisfy the public grammar and exactly equal the expected canonical string, including precision and spelling.
- `source_observation_ids` must be lexicographically sorted and unique; `seen_id_set` must contain strictly increasing unique positive integers. Equality is exact ordered-list equality. The limits are eighteen observation IDs and eighty seen release IDs. `opening_eligibility` has at most five canonical positive decimal-string keys and exact boolean values. Map-key order is irrelevant; key/value membership is exact.
- Required support is the unique sorted eligible set independently listed by C16. Candidate support order is irrelevant. Every required reference must be present. Additional eligible IDs are allowed and reported once per distinct additional ID; every repeated eligible occurrence after its first is separately reported as a duplicate. Extras and duplicates cannot erase full support or prevent completion. Every invalid reference occurrence is reported and defeats the affected field's supported-content match, even if all required IDs also occur. Invalid includes malformed IDs, nonexistent IDs and excluded/unavailable observations. Observation-level eligibility is not span-level entailment.
- An unknown oracle value remains `oracle_unknown`, never wrong or removed from the planned denominator. Its support completeness, missing support and additional support are null because no full set is established; supplied eligible IDs and duplicates remain visible. Missing candidate output remains missing, including when the expected value is unknown. Missingness and oracle unknown counts therefore overlap intentionally.
- Unknown root/answer/provenance keys, wrong types and missing required keys are explicit schema failures. A parseable response retains diagnostics and supported-content matches for unaffected fields. A malformed root or missing/non-object answer/provenance map has no values/support from that map. Unparseable JSON has zero matches. An extra key can leave six or ten per-field content matches while making `content_complete` false. No hidden penalty changes the other fields.
- Malformed or inconsistent oracle evidence raises `CheckerRefusal`, never a candidate error or a zero score. The checker validates envelope keys, declaration identity, family grammar, sorted unique observations/inventory, admitted eligibility, known/unknown status, support availability and C16 support conventions. Known common fields require question-only support; known source membership equals the complete eligible set; release membership and history have consistent availability; opening support contains the question and one admitted release; obligation dependencies require all three admitted receipt kinds. A non-null oracle family must equal the public planned family. A valid null-family oracle leaves six/ten unknown fields and zero evaluable fields. These internal checks do not independently re-derive raw truth, identify which admitted release is the opening, or authenticate metadata.

Both JSON inputs are capped at 65,536 bytes, with no truncation. Duplicate keys, malformed UTF-8, BOM, nonfinite literals and trailing non-whitespace refuse parsing. Finite decimal lexemes must round-trip without changing decimal value. Python's unchanged integer-digit and recursion limits apply, including decimal map keys; numerical/runtime inability in oracle evidence is a refusal and in candidate evidence an explicit parse/field failure. Decimal conversion/comparison runtime failures use the explicit `numeric_limit` path: candidate diagnostics or oracle `CheckerRefusal`. This reports a runtime inability to interpret a numeric lexeme, not a claim that its JSON syntax is invalid. No global numeric settings are changed. Candidate provenance multiplicity is bounded by the byte cap, allowing duplicates without inventing an eighteen-entry reference-list limit. There is no output text expansion of source data; the returned dictionary is bounded by the input sizes and six/ten fields.

Top-level counts report planned fields, evaluable fields, oracle unknowns, value matches, missing and wrong values, invalid values, supported-content matches, fields missing required support, invalid reference occurrences, additional distinct eligible references and duplicate eligible occurrences. Per-field diagnostics preserve those distinctions. Counts are not a full study aggregate and no fraction is silently substituted for the planned denominator. The future eight-question pilot has 64 fields per arm; a single invented release has six and a single invented obligation has ten.

## Validation order and bounded comparison

First, independently specified literal tests freeze exact expected results without importing oracle/candidate fixture helpers. They cover both families, directional roles, correct/wrong/missing/unknown values, null-family planning, support inclusion and extra/duplicate/invalid references, exact types/list/map semantics, malformed oracle consistency, byte/collection/numeric limits and absence of effects/input mutation. First failures are retained before any correction.

After that policy and initial literals are frozen, exactly the existing C16 `expected-freeze-v1/release` and `expected-freeze-v1/obligation` baseline directories are selected. Their raw manifest/body files and hand-written expected answer/support artifacts, current oracle/normalizer/views/store source files and comparison recipe are hashed before execution. No other fixture replaces these two. The private bounded harness reads those frozen files directly; it does not import fixture builders.

For each selected fixture, the harness derives the C16 envelope once and verifies its answers/support exactly equal the pre-existing independent literal artifact. A disagreement is retained as expected-evidence failure, not changed to fit a candidate. It normalizes raw bytes once, retains normalized bytes or refusal diagnostics, then calls each encoder once. It saves, flushes, hashes and rereads the exact encoding before passing only saved bytes plus public field grammar to the decoder. Candidate functions never receive oracle answers. The harness retains each decoded output, checker result, exception and phase/outer timing. It performs no model calls, forecasts or original-study access. The one declared integration attempt is never rerun to replace a failure, and no candidate/oracle component is changed here.

The [implementation record](./runs/2026-11-27-prospective-query-check.md) reports actual controls and both families separately. Candidate disagreement is diagnostic evidence for a later separately reviewed repair packet; it is not a checker-test failure to conceal. Five other families remain unmeasured. This is pre-registration engineering, with no assessment, collection, registration, prediction, learning, calibration, causal or business-advantage claim.
