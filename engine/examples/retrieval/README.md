# Frozen retrieval development inputs

These are owned questions and source references for the four-source local capture documented in [the B2b run](../../../docs/planning/runs/2026-11-25-graph-views.md). They do not contain the third-party article bytes. The matching evidence store must already retain the named snapshot and exact observations; fetching a changed live page is not reproduction of this corpus.

- `control-freeze.json` selects the four eligible observations and a stable corpus event ID.
- `control-queries.json` contains only candidate-visible query IDs and text. Add `corpus_id` and a fresh `run_key` to form a run request.
- `control-development.json` is evaluator input: eight supported questions, four corpus-unsupported questions, exact gold spans and limitations. Never pass this file to the candidate.

A curator prepared the cohort from retained bytes. A separate reviewer verified all twelve gold spans, supporting context for every positive question, and lack of the requested facts in the four-source corpus for the unsupported questions. Before any baseline run, “standard models” in the first question was clarified to “standard generally available models”; preview policy differs. No gold span changed. Questions and scoring rules are frozen before observing retrieval results.

The corpus is small and builder-visible. Unsupported means the requested fact is absent from these sources, not universally false. Gold spans are not an exhaustive inventory of every alternative supporting passage. The baseline returns passages, so an unsupported question receiving lexical matches is not itself a hallucinated answer.

The source snapshot is dated by the local collector. Later code, configuration and query artifacts describe the retrospective experiment; they are not evidence that the algorithm or questions existed at the earlier cutoff. No external timestamp proof is present.

`engine/tests/test_retrieval.py`, `test_retrieval_evaluation.py` and `test_retrieval_cli.py` use owned synthetic bytes to verify behavior without requiring the local development archive. Their results are conformance checks, not this corpus's retrieval quality. The [measurement contract](../../../docs/experiments/representation-metrics.md) defines the separate real development metrics and reproduction gate.

Its `retrieval_study` field binds the intended study; it is not a supplied score. The rest of the policy preserves the seven entity families, 30-second assessment limit, zero external spend and disabled scale changes.

Copy `control-study.json` to a private local file and replace its two placeholder absolute paths with the retained evidence store and this checkout's `control-development.json`. Paths can move; the declared content identities cannot. Do not point the evidence path at the dedicated improvement store or fetch current web pages to replace missing archived bytes.

Pass the resolved request with `--retrieval-study /absolute/path/to/study.json` on the existing improvement `assess` or `dispatch` command, using `control-improvement-policy.json` as its policy. Read the improvement status first and use its current predecessor and a fresh run key. Retained C1 events are validated and rescored; this does not launch a third search or change C1's questions. The controller records actual retrieval separately from its synthetic checks and preserves the original evidence store.

Both example files contain owned identifiers and hashes only. Source bytes, expanded local paths, captured bundles and process receipts belong in the private local archive. The [C2 run record](../../../docs/planning/runs/2026-11-25-retrieval-controller.md) records validation status and the real handoff separately from the examples.

## Compare the two fixed indexing representations

The same `--retrieval-study` handoff accepts a schema-2 study containing exactly two raw-window runs and two static HTML text-node runs. It validates and scores retained executions; supplying a study does not start searches. Execute the four runs in raw A, raw B, HTML A, HTML B order, completing each before starting the next. Every run uses the same corpus, ordered queries, search configuration, runner, indexing implementation, runtime, decoder and parser dependencies. Only the fixed recipe changes. Keep the existing development questions and gold untouched.

The request has `schema_version: 2`, `study_id`, `evidence_store`, `cohort_file`, `protocol_file`, `corpus_id` and `arms`. All three paths are absolute locators. `arms` has exactly `raw` and `html`, each containing `indexing_recipe` and two `run_terminal_ids`. The recipes are `raw-window-text-v1` and `static-html-text-nodes-v1`, respectively. The private study file supplies recorded terminal IDs, not result summaries.

The policy's schema-2 `retrieval_study` declaration binds the common snapshot ID/hash/manifest hash, corpus ID/hash, cohort/gold/query hashes, source/passages/config hashes and exact `protocol_hash`. Each declared arm contains its fixed `indexing_recipe`, `candidate_algorithm_hash`, and two maps keyed by its terminal IDs: `projection_hashes` and `run_terminal_hashes`. Candidate and output hashes come from verified receipts after execution; they are observed bindings, not evidence of preregistration. Retain the exact [comparison protocol](html-comparison-protocol.json) before execution separately from those post-run bindings. The adapter preserves protocol bytes and identity without interpreting arbitrary policy text as executable instructions.

Raw sources and citations remain unchanged: search results identify complete original byte windows. HTML projection supplies indexed text plus a checked mapping back to source bytes; a retrieved window covering a gold span does not establish that every gold byte survived projection. No answer generation or external model call is added. Numeric BM25 scores are not calibrated confidence and should not be compared across arms as confidence.

The neutral validation and scoring identity is separate from candidate identity. It includes the source/corpus, queries, gold, scoring code and shared decoder; it excludes the runner, indexing implementation and protocol description. Reports identify execution and candidate dependencies separately. A current rescore of a legacy receipt preserves its original execution fields; it does not replace the measurement identity recorded by the original historical assessment.

Both repeats in each arm must agree on projection, ordered results and evaluation. A valid disagreement reports reproduction zero, retains all four reports, omits quality deltas and queues repair. Once both arms reproduce under the common measurement, the controller queues fresh-question coverage evaluation for a gain, tie or regression. It retains the raw operational baseline and does not authorize adoption or another tuning cycle on visible gold. Earlier integrity and conformance failures retain priority.

The adapter captures one coherent evidence prefix into the separate improvement store without modifying the source store. It enforces at most 256 events, 128 artifacts, 4 MB per artifact, 16 MB per bundle and 1 MB per request/cohort/protocol. Replay uses captured bytes even if the original paths disappear. Reports include receipt-reported resources for all four executions; those inner times exclude locked revalidation and commit. Outer caller time and builder/reviewer cost remain separate, and whole-step cost is unmeasured. Production assessment and dispatch budgets remain 30 and 60 seconds.

The comparison protocol is retained as opaque hash-bound bytes, not executed or interpreted by the adapter. The supervisor must separately bind static input identities to its pre-run freeze and enforce any historical migration bridge before candidate execution. A valid four-receipt report proves the adapter's fixed input/order/reproduction checks; it does not independently prove preregistration timing or execution provenance.

## Prepare fresh complete-support coverage

C4 uses the [coverage protocol](../../../docs/experiments/retrieval-coverage.md), cohort schema 2 and study schema 3. The cohort records supported/unsupported pairs and alternative sufficient support bundles; every span inside a bundle is required. Schema-1 cases and scores keep their earlier meanings. Do not pass either cohort's labels or spans to the candidate: `project_queries` returns only IDs and question text.

`control-fresh-coverage.json` contains the twelve reviewed questions and exact source references. `coverage-protocol.json` fixes its original byte hash, projected queries, corpus and limits. These files contain no third-party source text. The matching archived source bytes and exact review artifact remain required for actual preparation; fetching a newer page or inventing a review record cannot reproduce the frozen study.

The same `--retrieval-study FILE` and policy `retrieval_study` transport has explicit `preparation` and `evaluation` phases. A preparation request has exactly `schema_version`, `phase`, `study_id`, `evidence_store`, `cohort_file`, `protocol_file`, `review_file`, `corpus_id` and `freeze_event_id`. All four locators are absolute. Evaluation adds exactly `run_terminal_ids`, containing the two completed terminals in the frozen order. Preparation has no future terminal IDs or output hashes.

Before assessment, `validate_coverage_preparation` accepts the exact bounded cohort/protocol/review bytes and an independently supplied expected historical `reference_terminal: {id, hash}`. It verifies that the retained raw candidate and runtime match the current guarded implementation without searching. Its returned `lineage` and candidate/scorer identities are validated metadata, not quality. `create_coverage_freeze` takes the same inputs plus two distinct intended `run_keys`, retains original bytes and creates one exclusive freeze. `get_coverage_freeze` validates that freeze before or after correctly ordered later executions without appending anything.

Run keys must satisfy the existing runner's 1–100 character alphanumeric grammar with `.`, `_` or `-`; projected queries must satisfy its compiler limits, including at most 64 terms. The corpus must return at least five results when available. Capture preflight accounts for the known raw projection and artifacts, both future event sequences and bounded metadata before writing, then rechecks under the append lock. Historical lookup checks the original prefix rather than treating completed runs as additional planned work. These checks do not reserve space against unrelated later growth; unknown result-report sizes retain their existing completion checks.

The schema-3 policy declaration binds `phase`, `study_id`, all snapshot/corpus/cohort/gold/query/source/window/config hashes, original `protocol_hash` and `review_hash`, `freeze_event_hash`, the exact reference terminal, `candidate_algorithm_hash`, `evaluator_identity_hash` and `runtime_hash`. Evaluation adds terminal and projection hash maps keyed by the two requested terminal IDs. Those maps identify observed outputs; the earlier freeze binds intended inputs and run keys. A changed scorer or candidate requires a new reviewed freeze, not a rewrite of an old one.

A ready assessment appears under `report.coverage_preparation` and selects `execute_fresh_coverage_baseline`. Its inventory describes actual questions, evidence structures and entity families; retrieval quality remains absent. After two fresh raw runs, phase `evaluation` records `report.actual_retrieval` with both selected-v2 evaluations. Both phases share the same frozen measurement identity, while their assessment identities and captured prefix endpoints differ. Historical reference outputs establish provenance only and never substitute for fresh quality.

The owned synthetic `coverage-smoke.py` exercises this entire route with four invented sources, six pairs, two real retrieval subprocesses and two real assessment dispatches. Run it from the repository root with `PYTHONPATH=engine python3 engine/examples/retrieval/coverage-smoke.py`. It requires no private source archive or network. Its fixture review identities and expected results are synthetic integration controls, not independent semantic review or a real-corpus performance claim. Use the pinned historical interpreter for the actual retained-source experiment.

## Diagnose a retained support gap

Schema 3 also accepts `phase: "support_diagnosis"` through the same transport. Start from the exact evaluation request and declaration; preserve their original input and two-terminal bindings. The diagnosis request adds `diagnosis_id`, `diagnosis_file`, `diagnosis_review_file`, `origin_file` and `focus_question_ids`. All new file locators are absolute. The declaration adds `diagnosis_id`, `origin_transition: {id, hash}`, `origin_step_id`, `diagnosis_hash`, `diagnosis_review_hash` and the same ordered focus IDs. Focus must be a nonempty subset of failed supported questions, in cohort order.

Export the actual original `improvement_completed` event from the dedicated improvement ledger into `origin_file`. Its full body already contains both original evaluation reports. The adapter retains this one bounded event; the controller compares it with the live predecessor at claim and completion. A plausible exported event cannot substitute for the actual queued result. The original action must be `inspect_fresh_support_failures`; use its exact step ID as `--after-step` and a new run key.

`retrieval_diagnosis.compute_support_findings` previews deterministic interval findings from retained receipts, the frozen cohort and that original event. It recomputes coverage without search, indexing or aggregate scoring. `check_support_diagnosis` then verifies a separate semantic-review artifact bound to the findings hash, exact returned-window hashes and investigator bytes. The investigator document is retained but not interpreted as a command or numeric result. See the [diagnosis protocol](../../../docs/experiments/retrieval-support-diagnosis.md).

The review contains schema version 1, contract ID `retrieval-support-diagnosis-v1`, diagnosis ID/hash, original transition/step, findings hash, investigator/reviewer IDs, ordered focus IDs, exposure `post_execution_builder_visible_development`, and one case per focus ID. Each case records `question_id`, `category`, `reviewed_windows_hash` and `rationale`. Categories are `retrieval_gap`, `annotation_gap` and `unresolved`. These remain attributed judgments; different local IDs do not authenticate independence.

The report appears under `report.support_diagnosis`, without a new quality score. It retains the full failed-case inventory and any deferred failures. Reviewed retrieval gaps with no deferred cases select `prepare_focused_support_followup`; annotation gaps, unresolved judgments or deferred cases select `clarify_support_diagnosis`. Earlier integrity/conformance repairs retain priority. Both successors prepare further work, with unknown cost/success probability and no scale change. The previous quality outcome remains `unmeasured`.

Investigator bytes are capped at 256 KiB, review at 128 KiB and the origin event at 1 MB. Findings and checked reports are capped at 256 KiB, within the unchanged aggregate capture limits. Captured assessment can run after original paths disappear. A fresh controller dispatch still needs its actual predecessor; identical terminal replay returns the earlier result rather than consuming the step again. These checks are local evidence validation, not independent historical timestamping or a new retrieval experiment.

## Accept a fixed clause probe

Schema 3 `phase: "support_probe"` reuses the frozen coverage request's common fields and adds absolute `origin_file`, `probe_protocol_file`, `probe_review_file`, `probe_envelope_file` and `probe_execution_file` paths. It omits `run_terminal_ids`: present terminal references come from the execution artifact. The declaration retains common coverage lineage and adds `origin_transition`, `origin_step_id`, `probe_protocol_hash`, `probe_review_hash`, `probe_envelope_hash` and `probe_execution_hash`. The execution hash binds post-run evidence; it is never presented as preregistration.

The origin must be the actual completed diagnosis whose queued action is `prepare_focused_support_followup`, with no deferred or unresolved cases. The exact inherited prefix must equal that diagnosis's accepted evidence head. The protocol fixes two clauses, two run keys, original support intervals, the raw candidate and resource limits. A separate attributed review binds protocol bytes. An envelope binds ordinary observation references for the protocol, review, supervisor and both requests, together with origin and current validator/candidate identities. Capture its exact bytes as observation `support-probe:{protocol_id}:envelope`, source `support-probe-envelope:{protocol_id}`, before either run starts.

The execution artifact contains version 1, `envelope_hash`, `envelope_capture: {id, hash}`, `evidence_head: {seq, id, hash}` and two ordered `slots`. Each slot retains its run key, request-file hash, status, caller/stdout/stderr observation references and actual start/terminal references. Observation references use the existing `{observation_id, event_hash, content_hash, size}` format. `not_started` has no artifacts or events; a timeout, launch failure or nonzero exit retains what actually exists. Never invent a terminal. The second run starts only after the first completion validates.

The adapter captures exact files and the complete declared evidence prefix, including partial inputs. Its initial capture refuses a stale declared head rather than hiding later executions. The checker runs only on captured bytes, verifies every receipt against its own request, then reports separate clause support and `joint_support_union_of_two_top5`. Two top-five lists have a larger selection budget and no shared rank. Incomplete evidence fails; valid disagreement retains both results with aggregate support unavailable. Both cases preserve the original cohort score.

A valid reproduced diagnostic selects `prepare_control_exchange_decision_pilot`; valid disagreement selects `repair_retrieval_reproducibility`. Their metric/target/probability/cost fields remain unknown and scale change stays disabled. No payment or control action runs. Existing integrity/conformance priorities, atomic completion/successor, exact replay and delivery-failure recovery remain unchanged. See the [public protocol](../../../docs/experiments/retrieval-fixed-clause-probe.md).
